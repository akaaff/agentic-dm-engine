## Commands

Python 3.13, managed via [uv](https://docs.astral.sh/uv/). Non-packaged app (`tool.uv.package = false`).

- Install deps: `uv sync`
- Lint: `uv run ruff check .` / format: `uv run ruff format .` / type-check: `uv run mypy .`
- Unit tests (fully offline): `uv run pytest`
- Tests needing a live Ollama: `uv run pytest -m llm`
- Tests needing this project's own API running: `uv run pytest -m integration`
- Tests needing a CUDA GPU + the local SD-Turbo pipeline: `uv run pytest -m imagegen`
- Vendor SRD data: `uv run python scripts/download_srd.py`
- Full autoplay (2 AI companions, zero human input, judge-scored transcript, real scene images, whole campaign scene chain): `uv run python -m src.cli.play --autoplay --campaign goblin_ambush_oneshot` (default; also `wolf_den_short_arc`, `kobold_warren_full`)
- Generate a new campaign via the teacher model: `uv run python -m src.cli.generate_campaign --size {one_shot,short_arc,full} --id <campaign_id>` - writes `data/campaigns/<id>.yaml` and its encounter(s), playable via `--autoplay --campaign <id>` immediately after.
- Generate a distillation training dataset, in chunks (each writes its own `data/training/raw/<task>_seed<N>.jsonl`, safe against a mid-run crash): `uv run python -m src.cli.generate_training_dataset --task intent_parser --n 2000 --seed 1 --workers 16` (repeat with `--seed 2`, `3`, ... for more chunks), then merge+curate once into `data/training/curated/<task>_{train,val,test}.jsonl`: `uv run python -m src.cli.generate_training_dataset --task intent_parser --merge`. Both directories are gitignored/regenerable.
- LoRA fine-tune the intent-parser student (needs a CUDA GPU; `--wandb` needs `uv run wandb login`, `--push-to-hub` needs `uv run hf auth login`): `uv run python -m src.cli.finetune_intent_parser --wandb --push-to-hub` (add `--max-train 200 --max-val 50 --epochs 1` for a quick smoke test). Adapter saved to `models/intent_parser_lora/` (gitignored).
- 3-way eval (base vs fine-tuned vs teacher, held-out test set; needs a CUDA GPU + live Ollama): `uv run python -m src.cli.evaluate_intent_parser --n 300` - writes `data/training/eval_results/intent_parser_eval.md` + `_predictions.jsonl` (committed).
- Run the game/autoplay with the fine-tuned parser instead of the teacher: set `INTENT_PARSER_BACKEND=finetuned` (transformers/peft) or `finetuned_ollama` (GGUF via Ollama - the fast one, see engineering log; default `teacher`). `SCENE_IMAGES_ENABLED=0` skips SD-Turbo (frees ~3GB VRAM so a student backend can share the card with the Ollama teacher). Day 27 end-to-end re-eval (judge scores + parse latency, all backends): `uv run python -m src.cli.eval_end_to_end --runs 2` -> `data/training/eval_results/intent_parser_end_to_end.md`.
- Day 27 detour - export the fine-tuned adapter as a fast, Ollama-served GGUF model instead of transformers/peft: `uv run python -m src.cli.export_intent_parser_model` (merges the LoRA adapter, saves to `models/intent_parser_merged/`, gitignored), then convert with a local `git clone https://github.com/ggml-org/llama.cpp` (needs the full repo, not a single curled file) - `uv run --with sentencepiece --with protobuf --with pyyaml python <llama.cpp>/convert_hf_to_gguf.py models/intent_parser_merged --outfile models/intent_parser.f16.gguf --outtype f16` (no quantization needed at 0.5B), then `ollama create dm-intent-parser -f models/Modelfile.intent_parser` (a one-line `FROM <absolute path>.gguf` - the daemon resolves relative paths against its own cwd, not the shell's). `evaluate_intent_parser`'s `--ollama-model dm-intent-parser` adds it as a 4th eval column.

- Run the backend: `uv run uvicorn src.api.main:app --port 8000`
- Frontend (Day 17+, `web/` - Vite + React + TypeScript): `npm install` then `npm run dev` (serves on :5173); `npm run lint` (oxlint), `npx tsc -b` to type-check.

## Architecture

See `README.md` for a summary and `DECISIONS.md` for the reasoning behind each major choice. Short version: `src/engine/` is a deterministic, LLM-free rules engine (dice/state/turn-order/movement/rules/conditions/character-creation/campaign); `src/graph/` wires LangGraph nodes (intent_parser, rules_engine, narrator, player_agent, judge, scene_image) around a shared `GameState`; `src/llm/` holds the Ollama client and prompt templates; `src/imagegen/` wraps the local SD-Turbo pipeline; `src/api/` is the FastAPI service (REST for character/campaign/companion data, WebSocket for live play); `web/` is the React+Vite frontend.

## Conventions to keep consistent

- **Live-verify before trusting.** Every day's plan step ends with a concrete live check (CLI/API/browser output diffed against a hand-computed fixture, or a saved eval table), not just "tests pass" - matching the pattern from `order-fulfillment-platform` and `agentic-rag-assistant`, which caught real bugs on nearly every build day.
- **Deterministic engine code gets exhaustive unit tests with hand-computed expected values; LLM/image-gen code gets live verification instead of mocking** - a mock only proves the mock is self-consistent, not that the real model call behaves as expected.
- **Commit in small, clearly-described batches**, one coherent chunk of work at a time, not one commit per day.
- Constructor-injected dependencies, matching the sibling repos' pattern.

## Engineering log (gotchas, in the order they were found)

**`uv run pre-commit run --all-files` crashed mypy with "INTERNAL ERROR", but `uv run mypy <same files>` directly never did.** Root cause: pre-commit batches/parallelizes a hook's file arguments across concurrent subprocess invocations once there are enough files, and multiple mypy processes racing on the same `.mypy_cache/` directory corrupts it - a known mypy footgun with its own documented fix. Confirmed by reproducing the exact file set pre-commit passes in one direct `uv run mypy` call (succeeded every time) versus letting pre-commit invoke it (failed). Fixed by adding `require_serial: true` to the mypy hook in `.pre-commit-config.yaml`, forcing pre-commit to run it as one non-parallel invocation.

**`from src.config import ...` didn't resolve under plain `uv run pytest`, unlike the sibling repos' `from app.config import ...`.** Neither sibling repo sets `pythonpath` in `[tool.pytest.ini_options]`, yet their tests import their top-level package fine - whatever makes that work there wasn't reproduced here (not investigated further; not worth the time). Fixed directly and explicitly by adding `pythonpath = ["."]` to `[tool.pytest.ini_options]` in `pyproject.toml`, which reliably puts the repo root on `sys.path` for test collection regardless of package-layout quirks.

**`Mapping[str, int]` did not accept a `dict[Literal["STR", ...], int]` argument under strict mypy**, even though every possible key is a plain string. `Mapping`'s key type parameter is invariant in typeshed (unlike its covariant value type), so a `Literal`-keyed dict is not considered a subtype of a `str`-keyed one. Fixed by typing `validate_standard_array`'s parameter as `Mapping[AbilityScore, int]` (the actual key type in play) rather than trying to generalize to `str` - direct dict-literal call sites in tests still type-check fine via mypy's bidirectional inference against that stricter parameter type.

**The CLI's trace printed the wrong round number for the last action of every round** - a display bug, not an engine bug, but worth remembering how it was caught. `run_scripted`'s verbose print used `state.round` *after* `resolve_action` returned, but `resolve_action` already advances `state.round` as part of the same call when a round wraps - so the action that ends round 1 printed as "[Round 2]". Confirmed the actual `Event.round` values stored in `state.events` were correct all along (captured before the turn-advance step runs) by dumping the raw event log directly and comparing against the printed trace - only the CLI's post-hoc `print()` needed fixing (capture `round_before = state.round` ahead of the call). A reminder that a convenience print statement can be wrong even when the underlying data model is right, and it's worth checking which one actually is before "fixing" anything.

**`fastapi.testclient.TestClient` emits a `StarletteDeprecationWarning` pointing at a package called `httpx2`.** Confirmed by reading the installed `starlette` (0.46.2) source directly: `starlette.testclient` now tries `import httpx2 as httpx` first, falling back to plain `httpx` with the deprecation warning. Not chased down further on Day 8 - it's a warning, not a failure, and the tests pass either way - but worth revisiting if `httpx2` turns out to be the real forward path before this project accumulates many more `TestClient`-based tests.

**The SRD's Bard class has two separate proficiency-choice pools (3 skills + 3 musical instruments), and `character_creation._validate_skill_choices` sums/pools every `proficiency_choices` entry together** - not obvious from the schema, and easy to get wrong when authoring a Bard companion. Confirmed live: calling `create_character` for a Bard with only 3 skill choices raises `"Bard requires exactly 6 skill choice(s), got 3"` - the fix is passing 6 items total (3 real skills + 3 instrument indices like `lute`/`flute`/`lyre`) in `chosen_skills`, which the validation accepts because it only checks pool membership, not semantic category. `data/companions/pip_larkspur.yaml` documents this inline since it's the one companion that hits it.

**A newly-connecting WebSocket client could silently never receive its own initial `awaiting_input` message.** `_send_awaiting_input(session)` searches the whole session for the *first* connection controlling the current actor and sends to just that one - correct for "an action resolved, tell whoever's turn is next," but it was also being called on every new connection's own setup, which means a second connection joining a session where an earlier connection already controls the same actor (true for every connection under Day 11's "one connection controls everyone" simplification) would find the *earlier* connection as the match and send it a duplicate, while the newly-connecting client got nothing. Caught live: a real two-connection test against an actual running server hung waiting for the second connection's `awaiting_input` that was never coming. Fixed by sending a personal, connection-scoped awaiting_input directly to a client on its own connect (checking only whether *that* connection controls the current actor), separate from the shared session-wide search used after an action resolves.

**Starlette's `TestClient` WebSocket transport deadlocks with two connections open at once, even from separate `TestClient` instances** - draining all of one connection's queued messages before touching the other's blocks the server mid-broadcast (it looks like a rendezvous-style channel, not an arbitrarily-buffered queue, though this wasn't fully root-caused). The fix wasn't message-ordering tricks - genuine multi-connection tests now spin up a real `uvicorn.Server` in a background thread and use the real `websockets` client library for actual concurrent connections; `TestClient` is kept for single-connection tests, where it works fine.

**The intent-parser prompt only explicitly explained "attack"/"move"/"dash"/"invalid" in its Rules section - even though every verb appeared in the JSON schema's enum - and `qwen2.5:7b-instruct` defaulted to "invalid" for "I dodge incoming attacks", "I disengage and back away from combat", and "I use a healing potion" (dodge/disengage/use_item), all reasonable unambiguous player intents.** Confirmed live via the golden-set test (`tests/llm/test_intent_parser.py`) failing on exactly those three cases, passing on attack/invalid (the two verbs the prompt actually described). The schema enum alone wasn't enough context for the model to map free text onto the less-common verbs - fixed by adding an explicit one-line description of every verb to the prompt (not few-shot examples, which weren't needed here); all 7 golden cases passed after that. Same underlying lesson the sibling `agentic-rag-assistant` repo hit with its router prompt ("zero-shot unreliable, needs explicit guidance for the less obvious branches") via a different mechanism (there it needed few-shot examples, here a verb legend sufficed).

**An unhandled `TurnEngineError`/`NotImplementedError` from the graph crashed the whole WebSocket connection instead of failing gracefully.** Caught live during Day 12's free-text verification: the LLM extracted `item_or_spell: "dagger"` for a *monster's* attack (a goblin has no action named "dagger" in its SRD stat block - only "Scimitar"/"Shortbow"), and separately, the intent-parser prompt describes 10 verbs (including dodge/cast_spell/skill_check/use_item/help/death_save) but `turn_engine.resolve_action` only actually implements attack/move/dash/end_turn (Day 7's deliberate scope) - both raised uncaught exceptions that killed the connection. Fixed by catching both exception types around the graph invocation in `api/ws/session.py` and sending an `{"type": "error", "detail": ...}` message back to the sender instead - safe because `resolve_action` validates before mutating in both failure paths, so the turn simply doesn't advance and the same actor can retry. The underlying gap (most verbs not yet implemented in the rules engine) is real and not fixed here - only the failure mode (crash vs. a reportable error) is.

**An intent-parser utterance that doesn't name a target lets the LLM pick badly** - "The goblin attacks again" (no target named) resulted in `goblin_2` attacking `goblin_1`, a friendly-fire mistake, because the prompt's "visible characters" list has no notion of sides/allegiance for the model to reason about. Not fixed - noted as a real limitation of routing monster turns through the same free-text intent-parser built for interpreting a *human's own* stated intent; monsters likely need their own simple targeting logic (or a dedicated prompt that already assumes "attack a PC") rather than guessing from an under-specified command, whenever monster-turn AI becomes its own concern (Day 13's player_agent work is the closest existing hook, but it's scoped to companions, not monsters).

**A character's `skill_proficiencies` could contain a literal duplicate entry** when a class-chosen skill overlapped with the background's automatically-granted one - caught immediately by adding the obvious test: Pip Larkspur (Bard, Acolyte) chooses `skill-insight` *and* Acolyte grants `skill-insight` automatically, so the naive `chosen + background` concatenation produced `["skill-insight", "skill-insight", ...]`. Harmless for the `in` membership check `_resolve_skill_check` actually does, but still wrong data - fixed with `dict.fromkeys(...)` (preserves order, dedupes) rather than a plain list concatenation.

**In-character phrasing for a skill check ("I try to intimidate the goblin") was misclassified as "invalid", while the mechanically-worded version ("I attempt an intimidation check") worked correctly** - confirmed by calling `intent_parser_node` directly with both phrasings side by side. The skill_check verb's prompt description asked for "something needing an ability/skill check" without examples mapping ordinary action verbs (intimidate, sneak, search, persuade, climb) to skills, so the model needed the word "check" to make the connection reliably. Fixed by adding explicit verb-to-skill examples to the prompt (same fix shape as Day 12's verb-legend gap, different specific cause - there the model needed a verb *description* it lacked, here it needed the *mapping* from natural phrasing to the abstract category). Locked in as a golden-set regression case.

**`use_item` rejected a perfectly valid request because of word order**: the real LLM parsed "I drink my healing potion" into `item_or_spell: "healing potion"` (natural adjective-noun order), but `_resolve_use_item` was exact-matching against the canonical SRD name `potion-of-healing` (noun-of-noun order) - normalizing case/hyphens wasn't enough since the *words themselves* are in a different order. Confirmed live by calling `intent_parser_node` directly with several natural phrasings before touching the engine. Fixed with a word-set match (`{"healing","potion"} <= set(words)`) instead of an exact string comparison - the same class of "don't assume the canonical name" lesson as Day 12's verb-legend gap, applied to item names instead of verbs.

**The SRD 5.1 only includes one background: Acolyte.** Confirmed live on Day 1 by actually inspecting `data/srd/5e-SRD-Backgrounds.json` after downloading it (1 entry) - not assumed from general D&D knowledge, which would suggest Soldier/Criminal/Folk Hero etc. are available too (they're not SRD content, they're in the core Player's Handbook, which this project deliberately doesn't use). Day 5's character creation wizard needs to either offer Acolyte only, or the project authors a small number of original (non-WotC) backgrounds itself - mechanically simple (skill proficiencies + equipment + one feature) and safe to invent, unlike races/classes/monsters/spells which stay strictly SRD-sourced. Decide this explicitly on Day 5 rather than assuming background variety exists.

**Day 15's first real autoplay run (2 AI companions, zero human input) hung forever on the very first non-trivial persona.** Root cause #1: `player_agent`'s initial prompt asked a companion to "declare what it does" without ever enumerating the actual verb set, so a "quiet, watchful ranger, slow to warm up to strangers" persona (Silvana) happily generated pure atmosphere - "stays alert, watches the shadows" - forever. Since Day 14 deliberately made "invalid" a no-op that *doesn't* cost a turn (the right call for a human who can just retry), a companion with no human to unstick it just looped on the same non-action every turn. Fixed by rewriting `player_agent.md` to enumerate the same verb set intent_parser's own prompt uses and require exactly one concrete action, plus a `consecutive_invalid` circuit breaker in `cli.play.run_autoplay` that forces `end_turn` after 3 straight non-actions (defense in depth - the prompt fix alone isn't provably 100% reliable against a 7B model). Root cause #2, found immediately after fixing #1: the forced `end_turn` fallback itself was rejected once a companion went unconscious, because `resolve_action`'s top-level guard only accepts `"death_save"` while `hp<=0` - so the circuit breaker's own fallback action failed too, forever, the same infinite loop one layer down. The real fix belongs in `player_agent_node` itself (not just the autoplay script, since live WebSocket play would hit the identical hang the moment a companion goes down): an unconscious-but-not-dead companion is now forced straight to a `death_save` action, skipping the LLM call entirely - there's no narrative content to role-play in "try to stay conscious" anyway. Also gave `run_autoplay` the same `except (TurnEngineError, NotImplementedError)` resilience `api/ws/session.py` already had for human free text (Day 12) - an AI-declared move can still name a non-adjacent destination and get rejected by `movement.py`, and there's no human to phrase it better on retry, so the driver just logs the failure and tries again rather than crashing the whole run.

**Companion-vs-companion friendly fire, confirmed live on the same Day 15 autoplay run, then fixed.** Silvana (an AI companion) attacked Grom (a different AI companion, on her own side) twice in one encounter. This is the same underlying gap Day 12 already flagged for monster free text - `intent_parser`'s "visible characters" list has no notion of allegiance, so an under-specified utterance can resolve to any character id, ally or enemy - now confirmed to hit companion-vs-companion too, not just monster-vs-monster. Rather than patch it at the prompt layer again (no zero-shot prompt tweak can be *guaranteed* to stop a small model from occasionally picking a bad target), fixed it once at the one place both `_resolve_attack` and `_resolve_cast_spell` funnel through: a new `_validate_attack_target` rejects any attack where `target.is_pc == actor.is_pc` (same side, whichever side) before dice are ever rolled - a real game-rule the deterministic engine should own regardless of which upstream LLM call produced the bad target. Two hand-computed regression tests added (PC-attacks-PC, monster-attacks-monster) plus a cast_spell equivalent; the pre-existing "not fixed" monster-vs-monster note above is now closed by this same guard.

**`tests/llm/test_autoplay.py` failed on its first automated run** by hitting `run_autoplay`'s `max_turns` safety valve, even though a manual `--autoplay` run moments earlier finished cleanly (victory in 16 turns). Not a hang or a logic bug - confirmed the turn-advancement invariant holds (a failed/invalid action never advances `state.current_turn`, so the *same* stuck actor is correctly retried and the `consecutive_invalid` circuit breaker does eventually fire for it) - just LLM sampling variance: even with the Day 15 prompt fix, a companion's declaration occasionally still fails to parse, and each such failure burns a turn without landing an attack, which can stretch an already-unlucky combat (bad dice on top of wasted turns) well past a tight turn ceiling. Raised `max_turns` from 200 to 400 as a generous-on-purpose margin rather than chasing full reliability out of a small local model's free-text generation - consistent with `tests/llm/test_intent_parser.py`'s own framing ("LLM output isn't byte-deterministic... tolerant of everything else"). This test can still occasionally need a rerun; that's expected for anything exercising live sampling, not a regression to chase to zero.

**Day 16 - `uv add torch` alone installs a CPU-only wheel; getting the CUDA build needs an *additional* index, not a wholesale replacement of the default one.** `uv add torch --index-url https://download.pytorch.org/whl/cu124` failed dependency resolution entirely - `--index-url` replaces the *default* index for the whole resolve, so `alembic` and everything else in the project suddenly couldn't be found (PyTorch's wheel index only hosts PyTorch-ecosystem packages). Fixed with `uv add torch --index https://download.pytorch.org/whl/cu124` instead, which resolved and installed `torch==2.6.0+cu124` correctly. Note this is *not* as narrowly scoped as it sounds, though: `uv.lock` shows several common transitive deps (certifi, idna, packaging, requests, urllib3, numpy, pillow...) also got pinned to the pytorch index's mirror rather than PyPI, since `--index` adds it as an extra general-purpose index for the whole project, not a source pin restricted to torch alone - confirmed by grepping `uv.lock` for `download.pytorch.org` and finding ~35 packages attributed to it, not just torch. Not a problem in practice (the lockfile pins exact versions either way and everything resolved/tested clean), but worth knowing before assuming `--index` scopes as tightly as `[tool.uv.sources]` normally would. Confirmed live: `torch.cuda.is_available()` -> `True`, `torch.cuda.get_device_name(0)` -> the RTX 3080.

**The critical VRAM-coexistence check (this day's actual gate) passed, but the first measurement attempt gave a false "barely fits" reading purely from tool-timing mistakes, not anything about the GPU.** Querying `nvidia-smi` from separate sequential tool calls around a backgrounded generation script kept catching the process either before it had started or after it had already exited and freed its VRAM - the fix was mundane (run the generation script and a polling `nvidia-smi` loop inside *one* shell invocation, backgrounding the python process with `&` and polling every 3s), not anything about the measurement itself. Once measured correctly: baseline with only `qwen2.5:7b-instruct` loaded was ~5.85GB; with SD-Turbo's pipeline also loaded and a generation in flight, combined usage held steady at ~9.55GB out of 10GB - confirmed live, not estimated (see DECISIONS.md #5). Separately, a `uv run python <script>` invocation using an absolute script path outside the project directory needs either `cd`-ing into the project first or `PYTHONPATH` set explicitly - `pythonpath = ["."]` in `pyproject.toml` only affects `pytest` collection, not arbitrary script runs, so `from src...` failed with a plain `ModuleNotFoundError` until one of those was added.

**A real, load-bearing bug in the VRAM guard: after the very first successful generation, every subsequent scene image for the rest of a session was silently skipped with "Not enough free VRAM."** Caught live running `--autoplay` with real image generation for the first time - only round 1 got an image, rounds 2 onward all logged the skip warning despite the GPU being nowhere near actually out of memory. Root cause: `_has_enough_vram()` was being called before *every* `generate_scene_image()` call, but it checks `torch.cuda.mem_get_info()`'s free-bytes figure - which reports memory free to the *driver*, not to this process specifically. Once SD-Turbo's pipeline is loaded, PyTorch's caching allocator retains the VRAM blocks it already grabbed so it can reuse them for the *next* inference without asking the driver again - which is the whole point of the allocator, but it means "free" stays low from then on even though the already-loaded pipeline needs zero *new* memory to run again. Fixed by moving the VRAM check into `_load_pipeline()` (an `@cache`'d function that only ever runs once per process) so it gates the one-time decision "should we even attempt to load the model" rather than being re-asked on every call; a genuine later OOM is still a real exception caught by `generate_scene_image`'s existing broad except. Re-ran the full autoplay afterward and confirmed all 10 rounds got a scene image, not just the first.

**Verified live: `scene_image_node`'s prompts, built from `game_state.encounter_id` + a same/enemy-labeled character-and-HP summary (no access to the actual `Scene.narrative_intro` text, which isn't threaded into `GraphState` yet), still produced 10/10 images that were visibly on-theme** - armed fighters clashing with green goblin-like creatures in rocky/forested terrain, consistent with "goblin ambush" - spot-checked by eye (5 of 10) rather than assumed. SD-Turbo's 1-step inference can't render specific narrative details (a character being unconscious, an exact HP count), which is an accepted limitation of the "turbo" distillation at this step count, not a prompt bug.

**Day 17 - the Browser pane's `preview_start` reads `.claude/launch.json` relative to this session's own primary working directory (the user's home directory), not wherever a shell has `cd`'d to.** Adding a project-local `.claude/launch.json` in `agentic-dm-engine/` had no effect - `preview_start({name: "backend"})` silently ran an unrelated, pre-existing "web-client" config for a *different* project (`order-fulfillment-platform`) found in the home-directory `launch.json`, since that was the only entry and the name didn't match. Fixed by adding entries to the home-directory `.claude/launch.json` instead, using `uv run --directory <absolute path> ...` and `npm --prefix <absolute path> ...` so each command doesn't depend on any particular starting cwd. Kept the project-local `.claude/launch.json` too (with plain relative commands) since a plain terminal session started with cwd already inside the project would resolve it correctly.

**A brand-new character-creator submission failed with a browser-reported CORS error that had nothing to do with CORS.** The actual cause (visible only in the backend's own logs, not the browser) was `sqlite3.OperationalError: no such table: characters` - the dev SQLite file existed but had never had `alembic upgrade head` run against it in this checkout. Confirmed by reading `preview_logs` for the backend server, not by chasing the CORS message: FastAPI/Starlette's `CORSMiddleware` only attaches `Access-Control-Allow-Origin` to responses that complete normally through it; an unhandled exception (this SQLAlchemy error isn't an `HTTPException`, so `ExceptionMiddleware` doesn't catch it either) propagates past `CORSMiddleware` to the outer `ServerErrorMiddleware`, which converts it to a 500 *without* CORS headers - so the browser reports the symptom (missing CORS header) rather than the cause (a 500). Worth remembering for any future "CORS blocked" report on a route that otherwise has working CORS: check the server's own logs for an unhandled exception before touching the CORS config at all.

**A real, silent data-loss bug in the character-persistence layer, caught by the wizard's own re-fetch-after-create check** (exactly the kind of check Day 17's plan called for, and exactly why it's worth doing for real instead of assuming persistence works). `CharacterRecord` (the SQLAlchemy model, Day 8) predates `Character.class_index` (Day 14, needed for spellcasting-ability lookup) and `Character.skill_proficiencies` (Day 13) - neither field was ever added to the DB model or the two mapper functions (`_character_to_record`/`_record_to_character`), so every character ever created through the API silently lost both fields the moment they round-tripped through the database, for every class, not just spellcasters. First created a Fighter (no spells to lose) and didn't notice; only caught it by deliberately re-fetching and comparing against the create response, which is the actual point of that verify step. Fixed by adding both columns (`skill_proficiencies` needed `server_default='[]'` in the migration specifically - SQLite refuses to add a `NOT NULL` column with no default to a table that already has rows, caught immediately by just running the migration against the existing dev DB) and updating both mapper functions. Re-created a Wizard afterward and confirmed `class_index` and all four `skill_proficiencies` (2 chosen + Acolyte's 2 automatic) survived a real re-fetch.

**Day 18 - a character's `inventory` can contain the same equipment index repeated N times for a stacked item** (a Ranger's starting kit includes a quiver of 20 arrows, which `character_creation.py`'s `inventory.extend([index] * quantity)` expands into 20 separate `"arrow"` entries rather than one `"arrow"` with a count). Noticed live creating a Ranger through the wizard - the result sheet's inventory line read as 20 repeated words. Not a bug (the underlying data is correct and this expansion is pre-existing, documented Day 5 behavior - a flat list of item instances, not a quantity map) and out of scope to fix today - flagged here so a future inventory-display day (frontend `CharacterSheet.tsx`, or the engine itself) knows to group-and-count rather than assuming one entry means one item.

**Day 19 - `companion_ids` from the API (`Character.id`, e.g. `"companion_grom"`) and `load_companion_spec`'s argument (a YAML filename stem, e.g. `"grom_ironfist"`) are two different namespaces for the same companion, and conflating them was a real, silent bug.** Wiring a real session's party from a `CampaignProgress` row called `load_companion_spec(companion_id)` directly using the API-facing id - which raised `FileNotFoundError` (no `companion_grom.yaml` exists) inside `_build_real_session_game_state`'s defensive `try/except`, so the whole session silently fell back to the Day-7 demo skirmish instead of erroring loudly. Caught by an offline test asserting the exact character-id set in the resulting encounter (thorin/companion_grom/goblin_1-3), which failed with the demo's elrond/goblin_1/goblin_2 instead - a good example of why that kind of exact-set assertion is worth writing even when "it looks like it should work." Fixed with a new `load_companion_spec_by_character_id` lookup in `engine/companions.py`, used everywhere outside that module that only ever sees the roster via `Character.id`.

**Day 19 - a rejected WebSocket action (`TurnEngineError`) left the human unable to ever retry, even though the server-side comment already said "let them try again."** The turn correctly stays with the same actor (nothing mutated before the error), but `_handle_client_message`'s error path only sent `{"type": "error"}` and returned - it never re-sent `awaiting_input`. The frontend's `sendPlayerAction` optimistically clears its own "it's my turn" flag the instant it sends (so a second click can't double-submit while waiting), and had nothing to restore it once the error came back - so the input box stayed disabled forever after exactly one rejected action. Confirmed live: attacking with `"my fireproof toaster"` (not a real weapon) correctly showed the error text but left the box dead until this was fixed by also calling `_send_awaiting_input(session)` on the error path; verified the exact same session could then retry with a real weapon and the attack resolved normally.

**Day 19 - two false alarms while testing live, both worth recording so they're not re-chased next time.** (1) A long-lived browser tab's WebSocket appeared to stop receiving messages after many `preview_logs`/wait/screenshot cycles during debugging - independently verified via a second diagnostic WebSocket connection to the *same* session that the server-side state was completely correct the whole time, so this was environment/tooling flakiness in the extended debugging session, not an application bug; a fresh tab with a tighter test loop reproduced nothing wrong. (2) Several `computer{action:"screenshot"}` calls rendered a visually "stale-looking" frame (a disabled-vs-enabled input looking identical under the dark theme) that read as a bug at a glance - reading the actual DOM (`input.disabled`, `.textContent`) directly via `javascript_tool` settled it immediately and should be the first move when a screenshot's *meaning* is ambiguous, not just when it might be out of date.

**Day 20 - the Browser pane's `computer{action:"left_click", coordinate:[x,y]}` did not register real clicks on the SVG combat grid at coordinates independently confirmed correct via `document.elementFromPoint`.** Verified the target `<rect class="grid-cell clickable">` really was at that point in the page (`elementFromPoint` returned it), yet the simulated click produced no server round-trip (no narration, no error, no position change) - while a JS-dispatched `new MouseEvent('click', {bubbles:true})` on the same element worked immediately and correctly. Root cause not pinned down further (likely something about how this tool's pointer-event simulation interacts with SVG hit-testing or a coordinate-frame mismatch after `resize_window`, which separately also broke ref-based `computer` clicks entirely until the tab was returned to its default size) - treated as a testing-tool limitation, not application code, since a real DOM click event (what an actual mouse click produces) worked every time. When a `computer` click on a small/precise target silently does nothing and the element is confirmed present at that point, dispatching a synthetic click via `javascript_tool` is a reliable fallback for verification purposes.

**Day 21 - `resize_window` to a custom size intermittently breaks `computer` clicks/keypresses on regular DOM elements too, not just the SVG grid.** After resizing to 1100x750 for a wider portfolio screenshot, a `computer` click on the free-text action input followed by `type` and a `key: "Return"` submit produced no server round-trip at all - confirmed via `document.activeElement`/`input.value` that the click never actually focused the input the first time, and separately that pressing Return in a focused, correctly-filled input did not trigger the form's native submit-on-Enter behavior in this environment. Resetting to the `desktop` preset made plain `computer` click+type work normally again immediately. Settled the actual verification by calling `form.requestSubmit()` directly via `javascript_tool` once the input was confirmed genuinely focused and filled - same lesson as Day 20's SVG finding: a JS-dispatched interaction is the reliable fallback once a `computer` action's effect can't be confirmed through the DOM, and it's worth checking the DOM state instead of trusting that a click "must have landed."

**Day 21 - a live playthrough action can genuinely take 15-20+ seconds of real wall-clock time to fully resolve, well past what looks like "probably done by now."** After Cassian's attack, checking narration/character-sheet state after an 8s wait showed the *narration* for his kill already appended but the *character sheets* still showing the target goblin alive and Cassian still marked as the current actor - looked exactly like Day 19's WS-message-ordering false alarm at first glance. Waiting another ~8s and re-reading the same DOM showed everything fully caught up and consistent (goblin marked dead, round incremented, turn correctly back to the human) - the delay was real: `_autoplay_non_human_turns` chains several sequential live LLM calls (narrator + intent_parser per companion/monster turn) after the human's own action, and narration for the human's action can visibly arrive well before the whole chain finishes. Worth remembering before re-diagnosing an "inconsistent state" finding as a bug: check whether enough real time has passed for however many sequential LLM calls are queued up, not just whether a fixed short wait "should" have been enough.

**Day 22 - both `cli.play.run_autoplay` and `api.ws.session._build_real_session_game_state` had, since Day 15/19, silently walked a campaign's scene chain straight to the first combat scene and skipped everything else - their own comments already flagged this as "Day 22's job."** Filled the gap with a new `campaign_runner.py` module deliberately kept outside `turn_engine`/`GameState`: narrative-beat and skill-challenge scenes have no turn order or battle map, so forcing them through combat-shaped machinery would mean fabricating fake turn/round bookkeeping for nothing. Skill-challenge narration is authored per-scene (`SkillChallengeDef.success_text`/`failure_text`), not LLM-generated, matching how `narrative_intro` already works - only in-combat turn narration goes through the narrator LLM. `run_autoplay` now loops over the whole chain (walk to next combat via `campaign_runner`, play it via the existing per-encounter turn loop, continue from wherever that scene points next) rather than playing exactly one encounter, and takes a `campaign_id` so any campaign can be autoplayed.

**Day 22 - live-verifying `kobold_warren_full` surfaced a real, pre-existing (Day 14) simplification rather than a new bug: an attack against an already-unconscious party member has no special effect** (the SRD rule that a hit on a helpless creature auto-crits and counts as two automatic death-save failures was never implemented - Day 14's scope was explicitly "single-target attack-roll spells... a single healing potion," not the full unconsciousness rule set). A monster's attack against a downed PC just rolls to hit and deals damage that's clamped at 0 HP, doing nothing further - the downed character's fate is decided purely by their own independent death-save rolls each turn, uncoupled from whether they keep getting hit. This made one live combat (both companions going down near-simultaneously against a still-healthy third kobold) run 353 turns/119 rounds before ending in a real, correctly-detected defeat - confirmed not a bug by checking `_resolve_attack`/`_resolve_death_save` directly (no unconscious-specific branch exists) and by the run terminating cleanly well under the `max_turns=400` safety valve with no invariant violations. Not fixed - flagged here since it's a legitimate 5e-rules gap that would make combat pacing more realistic if a future day touches death saves again, same spirit as the Day 18 inventory-stacking note.

**Day 23 - constraining `monster_index`/`skill` to a dynamically-built `Literal` (turned into a JSON-schema `enum`) instead of a plain `str` eliminated an entire class of retries, confirmed by all 3 live generation runs succeeding on the first attempt with zero retries needed.** The only retries the validate-and-retry loop actually has to handle now are cross-field business rules a JSON schema can't express (scene count, combat-scene count) - genuinely rare in practice, since a 7B model given clear numeric guidance in the prompt mostly gets a simple count right. Worth remembering generally: whenever a structured-output field's valid values are a known closed set at generation time (even a set computed at runtime, not hardcoded), building the schema with that exact set as a `Literal`/enum is strictly better than a plain `str` field plus post-hoc validation - it makes the invalid case structurally unreachable instead of just detectable.

**Day 23 - a background shell process I'd started with plain `&` (not the harness's own background-task tracking) got orphaned when its parent tool call returned, and kept holding ~5GB of VRAM from a half-loaded SD-Turbo pipeline indefinitely** - `nvidia-smi` showed only 371MB free (down from the expected ~4GB+), and a subsequent real autoplay run crashed with a CUDA OOM *inside `torch.cuda.mem_get_info()` itself*, before ever attempting to load anything - apparently even querying free memory can fail if there isn't enough headroom left for CUDA to do the query. Found by checking `nvidia-smi`'s process list directly (a stray `python3.13.exe` computing on the GPU, distinct from Ollama's `llama-server.exe`) rather than assuming the GPU itself was the problem; `taskkill`ing that one orphaned PID immediately freed the memory and the next run succeeded normally. Not an application bug - a reminder that this project's own background-verification runs need the harness's tracked backgrounding (which reliably reports completion/failure), not ad-hoc shell `&`, specifically because an orphaned GPU-resident process doesn't announce itself the way a crashed foreground command does.

**Day 24 - the generic toolkit's actual "is this genericity real" test needed a task that couldn't accidentally share assumptions with `ParsedAction`.** Reused the plan's own suggested toy task (extract a person's name+age from a sentence, a 2-field schema with nothing resembling a game action) specifically so the pipeline couldn't pass by coincidence - a toy schema that happened to share `ParsedAction`'s shape (a `verb`-like field, a `target`-like field) wouldn't have proven the boundary was real. Ran clean on the first live attempt: all 3 pipeline stages (generate/curate/evaluate) worked against a schema and prompt the code had never seen, no changes needed.

**Day 25 - a synthetic scenario's placeholder character id, the literal word "actor", confused the teacher into mislabeling `ParsedAction.actor` in 146/300 (49%) of a real generated dataset.** Caught by the plan's own "spot-check 10 examples" verify step - the mismatch pattern (the model inventing "actor_0"/"actor_1" or substituting a different visible character's id) only ever happened when the expected id was literally "actor", confirmed by grepping all 146 mismatches. Not a production bug (the real game only ever uses proper name-based or slug ids - "thorin", "companion_grom", "goblin_1" - never the bare word "actor"), but bad training signal, since `resolve_action`'s real actor-mismatch check (`TurnEngineError` "It is X's turn, not Y's") would reject exactly this pattern if it ever occurred live, so training on it would teach a lesson about a case that can't happen at inference time. Fixed by giving the synthetic actor a name-based id instead of the generic placeholder - regenerating dropped the mismatch rate to 7/300 (2.3%, mostly harmless casing slips), in line with ordinary 7B noise already accepted elsewhere in this project. General lesson, worth remembering beyond this one field: a synthetic-data placeholder that reads as an English word/role description rather than a plausible real value can itself become the confound, not the thing actually being tested.

**Day 25 follow-up - scaled the intent-parser dataset from 300 to 10,000 examples, verified Ollama's concurrency and its real ceiling empirically rather than assuming a documented default.** `OLLAMA_NUM_PARALLEL` has no hard max - it's an unbounded env var, limited in practice by GPU memory (KV cache scales with parallel slots x context length). A trivial "say banana" prompt scaled cleanly to 64 concurrent requests with zero errors and flat VRAM, but that doesn't reflect the real workload - measured directly against this project's actual intent-parser prompt/schema (longer context, grammar-constrained JSON output) instead: 8 sequential real calls took 23.2s, 16 concurrent took 11.1s for double the work (~4x effective throughput, with real per-call variance 4-11s, unlike the flat trivial-prompt result) - the number that actually mattered for planning the generation run, not the toy benchmark. Also found that scaling example *count* alone wouldn't have bought much: the original template banks were only 3-7 phrasings per category, so more volume on the same templates just repeated ~40-50 sentences with different game-state context glued on. Expanded every category's phrasing bank substantially before scaling up - the final 10k-example run showed 870 unique surface utterance texts (vs. a linear extrapolation of ~150 unique texts if the old narrow banks had just been resampled 33x more).

**Day 25 follow-up - `generate_dataset`'s concurrency needed prompts built sequentially before any threading starts, not interleaved with it.** `task.generate_prompt()` closures typically wrap a shared `random.Random` instance (see `intent_parser_task.py`), and `random.Random` isn't safe to call from multiple threads at once - a naive "dispatch generate_prompt+chat_structured together per worker thread" design would have produced a subtly corrupted/non-reproducible random sequence. Fixed by building the full list of `n` prompts up front on the calling thread (fast, pure computation) before handing only the slow I/O-bound teacher calls to a `ThreadPoolExecutor` - no shared mutable state touched from more than one thread at any point. Ran 5 chunks of 2,000 (seeds 1-5, 16-way concurrency each) with zero validation failures and zero crashes across all 10,000 examples; merged and curated into a leak-free 7,000/1,500/1,500 split with zero duplicates found even across all 5 independently-seeded chunks (expected - see the actor-id-fix entry above: full prompts embed enough randomized game-state detail that exact-string collisions are vanishingly unlikely, so cross-chunk dedup is a cheap safety net, not something doing real work here). Final actor-mismatch rate across the whole 10k: 49 (0.49%), consistent with the 300-example post-fix measurement.

**Day 26 - `uv add trl` silently resolved to trl 0.11.4 + `datasets==1.1.1` (2020-era), which then crashed on import against the modern `pyarrow` in the env (`module 'pyarrow' has no attribute 'PyExtensionType'`).** Root cause was Day 16's cu124 PyTorch `--index`: it mirrors its own (stale) copies of common packages like `requests`, and uv's default "first index wins" dependency-confusion-safe resolution then refuses to consider PyPI's newer `requests` once it finds a match there - forcing every dependency that needs `requests>=2.32.2` (modern trl/datasets) down to an ancient version. Fixed with `index-strategy = "unsafe-best-match"` in `[tool.uv]` - uv's own suggested fix, and safe here because both indexes are ones this project explicitly configured and trusts (official PyPI + official PyTorch), not the untrusted-third-party scenario that flag guards against. Resolved cleanly to trl 1.12.0 + datasets 5.0.1 afterward. General lesson: a loose extra `--index` doesn't scope as tightly as `[tool.uv.sources]` and can quietly hold back unrelated dependency upgrades months later.

**Day 26 - the fine-tune worked on the first real run; the informative comparison was making the base-model column a fair fight.** Qwen2.5-0.5B-Instruct fine-tuned on the 10k dataset (3 epochs, LoRA r=16, bf16, no quantization, ~56 min on the RTX 3080) went from **0% valid `ParsedAction` / 13% verb accuracy** (base, zero-shot on the production prompt) to **100% valid / 96% verb / 98.4% overall field accuracy** - within 0.6pp of the 7B teacher's 99.0%. The base 0.5B model isn't broken - it emits valid JSON 100% of the time - it just doesn't know the schema contract (drops the required `actor` field, so *nothing* validates as a real `ParsedAction`). That 0% is the honest number for "drop this model into production as-is on the one prompt the game actually sends," which is exactly the question the distillation answers. Eval deliberately runs base and fine-tuned through plain `transformers.generate()` (no grammar constraint) while the teacher gets Ollama's constrained decoding - so the table reports valid-JSON rate, strict-ParsedAction rate, and field accuracy separately rather than one blended score that would let "learned to format JSON" masquerade as "learned the right verb". Weakest fields for the fine-tune (and the teacher): `params.path` (move coordinates, ~86% vs ~89%) and `params.skill` (skill-name inference, ~86% vs ~93%) - the two that need real value synthesis rather than copying a token from the prompt.


**Day 27 - swapping the distilled student into the live loop worked; the latency win didn't materialise, and the reason is the interesting part.** `config.INTENT_PARSER_BACKEND=finetuned` routes the live `intent_parser` node to `llm/local_parser` (base + LoRA via transformers/peft) instead of the Ollama teacher. A full in-browser playthrough confirmed it: free-text "I attack goblin_1 with my longsword" and "I try to intimidate the goblins into fleeing" both parsed correctly and resolved, and every companion turn auto-played through it across three rounds. Judge scores over 2 autoplay runs each: fine-tuned [6,7] vs teacher [7,7] - equivalent play, the swap doesn't degrade the game. But parse latency was a wash: student 2.7s vs teacher 2.9s median, despite 14x fewer parameters. The naive `transformers.generate()` path (bf16 weights, per-token Python overhead, no exact stopping) gives up almost everything the smaller model should win - first pass was 5.5s until `merge_and_unload()` + `max_new_tokens` 256->96 + an explicit `<|im_end|>` stop token got it to 2.7s. The real win needs the student on the same engine as the teacher (llama.cpp: q4, fused kernels, grammar-constrained stopping). Ollama 0.33's experimental safetensors importer can't do it on Windows (needs Apple MLX), and the standalone llama.cpp GGUF converter is no longer a single self-contained script - so GGUF->Ollama stays a Phase 8 item. Worth remembering: at the 0.5-7B scale on one machine, the inference stack dominates the parameter count for latency - "distill to something smaller" only pays off in speed if you also serve it as efficiently.

**Day 27 - one shared limitation surfaced live, not a fine-tune regression: a relative target reference ("the closest goblin") parsed as `verb=attack` with `target=null`, which `_resolve_attack` rejects ("attack action requires a target").** The teacher hits this too - resolving "closest"/"nearest" to a specific character id needs spatial reasoning the prompt doesn't spell out. Naming the id explicitly ("goblin_1") worked first try. Not chased further; it's a prompt-design gap that predates the distillation.

**Day 27 detour - the GGUF conversion Day 27 abandoned as Windows-blocked wasn't actually Windows-blocked; it was one incomplete download.** Re-attempted by cloning the *full* `llama.cpp` repo (not `curl`-ing the single `convert_hf_to_gguf.py` file, which is what actually failed on Day 27 - it imports a local `gguf-py` package and a `conversion` package that only exist alongside it in the repo). With the full clone, conversion to F16 GGUF (no quantization - unnecessary at 0.5B, and skipping it also means skipping the C++ build toolchain entirely, no `cmake`/`llama-quantize` needed) ran locally on Windows in under 5 seconds, using the project's *existing* venv (torch/transformers already installed) plus three lightweight ephemeral deps via `uv run --with`. Importing the resulting `.gguf` into Ollama hit a second, unrelated snag: `ollama create` reported "invalid model name" regardless of the name tried, for a `FROM ./relative/path.gguf` Modelfile - the real cause was the path being resolved against the `ollama serve` daemon's own working directory, not the calling shell's; an absolute path fixed it immediately. Confirms the actual, narrower blocker from Day 27 was specifically Ollama's *experimental* direct-safetensors importer needing Apple MLX - a real GGUF, produced this way, imports via the ordinary `Modelfile` path with no MLX involvement on any OS.

**Day 27 detour - Ollama's grammar-constrained decoding, which helps the 7B teacher, actively corrupted the GGUF-served fine-tuned student's output on one field.** The first live eval column for the new backend showed field accuracy *drop* (98.4% -> 91.2%) with two fields cratering to exactly 0%: `params.path` and `params.skill` - not degraded, always wrong the *same* way (`params: {}`), which doesn't look like quantization noise (there wasn't any) or genuine model damage from the conversion. Confirmed by direct comparison at the same prompt/temperature: unconstrained decoding (`chat`, no `format`) produced the correct `params.path`; `chat_structured`'s grammar-constrained decoding on the identical request produced `{}`. Root cause: `ParsedAction.params: dict[str, Any]` (`src/engine/actions.py`) is untyped, so its JSON-schema-to-grammar compilation has no per-key structure to guide generation, and the fine-tuned 0.5B - never trained under this specific constraint, unlike the teacher's general instruction-following which pushes through it anyway - takes the grammar's easiest valid completion, an empty object, instead of synthesizing the right nested keys. Fixed with a new generic `chat_structured_best_effort` (`llm/providers.py`): unconstrained `chat()` + best-effort JSON extraction + validate + retry (greedy then sampled), the same no-grammar shape `local_parser.parse_intent_local` already uses for the transformers-served student - re-running the eval afterward gave 98.3%, matching the transformers-served number almost exactly and confirming the GGUF conversion itself was lossless all along.

**Day 27 detour - a live, unrelated bug found while chasing a confusing latency measurement: `httpx` resolving `"localhost"` added a flat ~2.2s to *every* Ollama call on this Windows machine, independent of model, prompt, or GPU load.** First noticed as wildly inconsistent latency readings for the exact same code path (sub-second in one micro-benchmark, ~2.7-3.4s moments later for what should have been the identical request) - ruled out GPU contention directly (confirmed via `ollama ps` showing 100% GPU residency for both models, and the gap persisting unchanged with the GPU completely idle, 13% util). Isolated by comparing Ollama's own self-reported `total_duration` against this project's wall-clock measurement for the identical request: a consistent ~2.2-2.3s gap neither the model nor the GPU could account for. Confirmed root cause by pointing the same request at `127.0.0.1` instead of `localhost`: the gap vanished (2.8s -> 0.65-0.96s) - the classic Windows IPv6-loopback-resolves-first-with-slow-fallback issue. This had been silently taxing *every* LLM call this whole project makes (narrator, player_agent, intent_parser, judge, the training/eval pipeline) since Day 12, not something specific to this detour's new backend - just the first time a clean enough isolated benchmark surfaced it. Fixed by changing `OLLAMA_BASE_URL`'s default in `config.py` to the literal `http://127.0.0.1:11434`.

**Day 27 detour - final honest end-to-end numbers, after both fixes above, and which fix actually mattered.** `teacher` ~1000ms median parse latency (down from the original Day 27 table's 2938ms; measured 726-1018ms across reruns - real run-to-run noise, still a ~3-4x drop either way), `finetuned` (transformers/peft) ~2700-2730ms (unaffected by the `localhost` fix - it never goes through Ollama), `finetuned_ollama` (GGUF, same llama.cpp engine as the teacher) ~460-510ms, field accuracy 98.3% (within a point of both the transformers-served fine-tune's 98.4% and the teacher's 99.2%). Judge scores noisy across both runs ([7,7]/[7,6]/[6,7] scattered across backends) - within the already-documented LLM-sampling variance, not treated as a quality signal on a 2-sample size. Exact figures in `data/training/eval_results/intent_parser_end_to_end.md` are whichever run was most recently committed.

Reflecting on these numbers honestly (prompted by the user pushing back that a ~200-300ms-per-parse-call win "was not that big"): the `finetuned_ollama` backend swap itself - roughly half the now-fast teacher's latency - is a real ~2x win, but not one a player would feel; it's one call out of several chained per turn, and the absolute savings is a few hundred milliseconds. **The `localhost` fix was the actual headline result, not a supporting detail** - it speeds up *every* LLM call the app makes (narrator, player_agent, judge, intent_parser regardless of backend), not just this one new backend. Verified directly rather than just inferring it from the isolated parse-latency numbers: a full `run_autoplay` of the goblin one-shot (scene images off, teacher backend - i.e. the app's actual default configuration) now averages **~7.1s/round**, down from Day 21's documented "15-20+ seconds/round" for the same kind of multi-companion round (that estimate also included scene-image generation, so the LLM-call-only improvement is likely larger still). The lesson worth keeping: a benchmark chasing one specific optimization can surface a much bigger, unrelated one, and the unrelated one is what's worth leading with when writing up the result - not the thing the benchmark was originally built to measure.
