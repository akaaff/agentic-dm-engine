# CLAUDE.md

Guidance for working in this repository, in the sibling repos' own convention: commands first, then an engineering log of real gotchas hit while building it - the "why" behind non-obvious decisions, not a restatement of what the code already says.

## Commands

Python 3.13, managed via [uv](https://docs.astral.sh/uv/). Non-packaged app (`tool.uv.package = false`).

- Install deps: `uv sync`
- Lint: `uv run ruff check .` / format: `uv run ruff format .` / type-check: `uv run mypy .`
- Unit tests (fully offline): `uv run pytest`
- Tests needing a live Ollama: `uv run pytest -m llm`
- Tests needing this project's own API running: `uv run pytest -m integration`
- Tests needing a CUDA GPU + the local SD-Turbo pipeline: `uv run pytest -m imagegen`
- Vendor SRD data: `uv run python scripts/download_srd.py`
- Full autoplay (2 AI companions, zero human input, judge-scored transcript, real scene images): `uv run python -m src.cli.play --autoplay`
- Apply DB migrations (required before the API can persist anything): `uv run alembic upgrade head`
- Run the backend: `uv run uvicorn src.api.main:app --port 8000`
- Frontend (Day 17+, `web/` - Vite + React + TypeScript): `npm install` then `npm run dev` (serves on :5173); `npm run lint` (oxlint), `npx tsc -b` to type-check.

(Training commands will be added here as each phase lands - see `C:\Users\yakra\.claude\plans\radiant-waddling-hellman.md` for the full day-by-day plan.)

Ollama must be running on the host with `qwen2.5:7b-instruct` pulled for anything touching `tests/llm` or the live intent-parser/narrator nodes (Phase 3+). `torch`/`diffusers` need a CUDA-enabled torch build - installed via `uv add torch --index https://download.pytorch.org/whl/cu124` (plain `uv add torch` pulls a CPU-only wheel; `--index-url` instead of `--index` breaks resolution of the rest of the project's dependencies, since it replaces the default index globally rather than scoping to just this package).

## Architecture

See `README.md` for a summary and `DECISIONS.md` for the reasoning behind each major choice. Short version: `src/engine/` is a deterministic, LLM-free rules engine (dice/state/turn-order/movement/rules/conditions/character-creation/campaign); `src/graph/` wires LangGraph nodes (intent_parser, rules_engine, narrator, player_agent, judge, scene_image) around a shared `GameState`; `src/llm/` holds the Ollama client and prompt templates; `src/imagegen/` wraps the local SD-Turbo pipeline; `src/api/` is the FastAPI service (REST for character/campaign/companion data, WebSocket for live play); `web/` is the React+Vite frontend.

## Conventions to keep consistent

- **Live-verify before trusting.** Every day's plan step ends with a concrete live check (CLI/API/browser output diffed against a hand-computed fixture, or a saved eval table), not just "tests pass" - matching the pattern from `order-fulfillment-platform` and `agentic-rag-assistant`, which caught real bugs on nearly every build day.
- **Deterministic engine code gets exhaustive unit tests with hand-computed expected values; LLM/image-gen code gets live verification instead of mocking** - a mock only proves the mock is self-consistent, not that the real model call behaves as expected.
- **Commit in small, clearly-described batches**, one coherent chunk of work at a time, not one commit per day.
- Constructor-injected dependencies, matching the sibling repos' pattern.

## Engineering log (gotchas, in the order they were found)

**`uv run pre-commit run --all-files` crashed mypy with "INTERNAL ERROR", but `uv run mypy <same files>` directly never did.** Root cause: pre-commit batches/parallelizes a hook's file arguments across concurrent subprocess invocations once there are enough files, and multiple mypy processes racing on the same `.mypy_cache/` directory corrupts it - a known mypy footgun with its own documented fix. Confirmed by reproducing the exact file set pre-commit passes in one direct `uv run mypy` call (succeeded every time) versus letting pre-commit invoke it (failed). Fixed by adding `require_serial: true` to the mypy hook in `.pre-commit-config.yaml`, forcing pre-commit to run it as one non-parallel invocation.

**`from src.config import ...` didn't resolve under plain `uv run pytest`, unlike the sibling repos' `from app.config import ...`.** Neither sibling repo sets `pythonpath` in `[tool.pytest.ini_options]`, yet their tests import their top-level package fine - whatever makes that work there wasn't reproduced here (not investigated further; not worth the time). Fixed directly and explicitly by adding `pythonpath = ["."]` to `[tool.pytest.ini_options]` in `pyproject.toml`, which reliably puts the repo root on `sys.path` for test collection regardless of package-layout quirks.

**`Mapping[str, int]` did not accept a `dict[Literal["STR", ...], int]` argument under strict mypy**, even though every possible key is a plain string. `Mapping`'s key type parameter is invariant in typeshed (unlike its covariant value type), so a `Literal`-keyed dict is not considered a subtype of a `str`-keyed one. Fixed by typing `validate_standard_array`'s parameter as `Mapping[AbilityScore, int]` (the actual key type in play) rather than trying to generalize to `str` - direct dict-literal call sites in tests still type-check fine via mypy's bidirectional inference against that stricter parameter type.

**The CLI's trace printed the wrong round number for the last action of every round** - a display bug, not an engine bug, but worth remembering how it was caught. `run_scripted`'s verbose print used `state.round` *after* `resolve_action` returned, but `resolve_action` already advances `state.round` as part of the same call when a round wraps - so the action that ends round 1 printed as "[Round 2]". Confirmed the actual `Event.round` values stored in `state.events` were correct all along (captured before the turn-advance step runs) by dumping the raw event log directly and comparing against the printed trace - only the CLI's post-hoc `print()` needed fixing (capture `round_before = state.round` ahead of the call). A reminder that a convenience print statement can be wrong even when the underlying data model is right, and it's worth checking which one actually is before "fixing" anything.

**`fastapi.testclient.TestClient` emits a `StarletteDeprecationWarning` pointing at a package called `httpx2`.** Confirmed by reading the installed `starlette` (0.46.2) source directly: `starlette.testclient` now tries `import httpx2 as httpx` first, falling back to plain `httpx` with the deprecation warning. Not chased down further on Day 8 - it's a warning, not a failure, and the tests pass either way - but worth revisiting if `httpx2` turns out to be the real forward path before this project accumulates many more `TestClient`-based tests.

**The SRD's Bard class has two separate proficiency-choice pools (3 skills + 3 musical instruments), and `character_creation._validate_skill_choices` sums/pools every `proficiency_choices` entry together** - not obvious from the schema, and easy to get wrong when authoring a Bard companion. Confirmed live: calling `create_character` for a Bard with only 3 skill choices raises `"Bard requires exactly 6 skill choice(s), got 3"` - the fix is passing 6 items total (3 real skills + 3 instrument indices like `lute`/`flute`/`lyre`) in `chosen_skills`, which the validation accepts because it only checks pool membership, not semantic category. `data/companions/pip_larkspur.yaml` documents this inline since it's the one companion that hits it.

**A newly-connecting WebSocket client could silently never receive its own initial `awaiting_input` message.** `_send_awaiting_input(session)` searches the whole session for the *first* connection controlling the current actor and sends to just that one - correct for "an action resolved, tell whoever's turn is next," but it was also being called on every new connection's own setup, which means a second connection joining a session where an earlier connection already controls the same actor (true for every connection under Day 11's "one connection controls everyone" simplification) would find the *earlier* connection as the match and send it a duplicate, while the newly-connecting client got nothing. Caught live: a real two-connection test against an actual running server hung waiting for the second connection's `awaiting_input` that was never coming. Fixed by sending a personal, connection-scoped awaiting_input directly to a client on its own connect (checking only whether *that* connection controls the current actor), separate from the shared session-wide search used after an action resolves.

**Starlette's `TestClient` WebSocket transport deadlocks with two connections open at once, even from separate `TestClient` instances** - draining all of one connection's queued messages before touching the other's blocks the server mid-broadcast (it looks like a rendezvous-style channel, not an arbitrarily-buffered queue, though this wasn't fully root-caused). The fix wasn't message-ordering tricks - genuine multi-connection tests now spin up a real `uvicorn.Server` in a background thread and use the real `websockets` client library for actual concurrent connections; `TestClient` is kept for single-connection tests, where it works fine.

**The intent-parser prompt only explicitly explained "attack"/"move"/"dash"/"invalid" in its Rules section - even though every verb appeared in the JSON schema's enum - and `qwen2.5:7b-instruct` defaulted to "invalid" for "I dodge incoming attacks", "I disengage and back away from combat", and "I use a healing potion" (dodge/disengage/use_item), all reasonable unambiguous player intents.** Confirmed live via the golden-set test (`tests/llm/test_intent_parser.py`) failing on exactly those three cases, passing on attack/invalid (the two verbs the prompt actually described). The schema enum alone wasn't enough context for the model to map free text onto the less-common verbs - fixed by adding an explicit one-line description of every verb to the prompt (not few-shot examples, which weren't needed here); all 7 golden cases passed after that. Same underlying lesson the sibling `agentic-rag-assistant` repo hit with its router prompt ("zero-shot unreliable, needs explicit guidance for the less obvious branches") via a different mechanism (there it needed few-shot examples, here a verb legend sufficed).

**An unhandled `TurnEngineError`/`NotImplementedError` from the graph crashed the whole WebSocket connection instead of failing gracefully.** Caught live during Day 12's free-text verification: the LLM extracted `item_or_spell: "dagger"` for a *monster's* attack (a goblin has no action named "dagger" in its SRD stat block - only "Scimitar"/"Shortbow"), and separately, the intent-parser prompt describes 10 verbs (including dodge/cast_spell/skill_check/use_item/help/death_save) but `turn_engine.resolve_action` only actually implements attack/move/dash/end_turn (Day 7's deliberate scope) - both raised uncaught exceptions that killed the connection. Fixed by catching both exception types around the graph invocation in `api/ws/session.py` and sending an `{"type": "error", "detail": ...}` message back to the sender instead - safe because `resolve_action` validates before mutating in both failure paths, so the turn simply doesn't advance and the same actor can retry. The underlying gap (most verbs not yet implemented in the rules engine) is real and not fixed here - only the failure mode (crash vs. a reportable error) is.

**An intent-parser utterance that doesn't name a target lets the LLM pick badly** - "The goblin attacks again" (no target named) resulted in `goblin_2` attacking `goblin_1`, a friendly-fire mistake, because the prompt's "visible characters" list has no notion of sides/allegiance for the model to reason about. Not fixed - noted as a real limitation of routing monster turns through the same free-text intent-parser built for interpreting a *human's own* stated intent; monsters likely need their own simple targeting logic (or a dedicated prompt that already assumes "attack a PC") rather than guessing from an under-specified command, whenever monster-turn AI becomes its own concern (Day 13's player_agent work is the closest existing hook, but it's scoped to companions, not monsters).

**A character's `skill_proficiencies` could contain a literal duplicate entry** when a class-chosen skill overlapped with the background's automatically-granted one - caught immediately by adding the obvious test: Pip Larkspur (Bard, Acolyte) chooses `skill-insight` *and* Acolyte grants `skill-insight` automatically, so the naive `chosen + background` concatenation produced `["skill-insight", "skill-insight", ...]`. Harmless for the `in` membership check `_resolve_skill_check` actually does, but still wrong data - fixed with `dict.fromkeys(...)` (preserves order, dedupes) rather than a plain list concatenation.

**In-character phrasing for a skill check ("I try to intimidate the goblin") was misclassified as "invalid", while the mechanically-worded version ("I attempt an intimidation check") worked correctly** - confirmed by calling `intent_parser_node` directly with both phrasings side by side. The skill_check verb's prompt description asked for "something needing an ability/skill check" without examples mapping ordinary action verbs (intimidate, sneak, search, persuade, climb) to skills, so the model needed the word "check" to make the connection reliably. Fixed by adding explicit verb-to-skill examples to the prompt (same fix shape as Day 12's verb-legend gap, different specific cause - there the model needed a verb *description* it lacked, here it needed the *mapping* from natural phrasing to the abstract category). Locked in as a golden-set regression case.

**`use_item` rejected a perfectly valid request because of word order**: the real LLM parsed "I drink my healing potion" into `item_or_spell: "healing potion"` (natural adjective-noun order), but `_resolve_use_item` was exact-matching against the canonical SRD name `potion-of-healing` (noun-of-noun order) - normalizing case/hyphens wasn't enough since the *words themselves* are in a different order. Confirmed live by calling `intent_parser_node` directly with several natural phrasings before touching the engine. Fixed with a word-set match (`{"healing","potion"} <= set(words)`) instead of an exact string comparison - the same class of "don't assume the canonical name" lesson as Day 12's verb-legend gap, applied to item names instead of verbs.

**The SRD 5.1 only includes one background: Acolyte.** Confirmed live on Day 1 by actually inspecting `data/srd/5e-SRD-Backgrounds.json` after downloading it (1 entry) - not assumed from general D&D knowledge, which would suggest Soldier/Criminal/Folk Hero etc. are available too (they're not SRD content, they're in the core Player's Handbook, which this project deliberately doesn't use). Day 5's character creation wizard needs to either offer Acolyte only, or the project authors a small number of original (non-WotC) backgrounds itself - mechanically simple (skill proficiencies + equipment + one feature) and safe to invent, unlike races/classes/monsters/spells which stay strictly SRD-sourced. Decide this explicitly on Day 5 rather than assuming background variety exists.

**Day 15's first real autoplay run (2 AI companions, zero human input) hung forever on the very first non-trivial persona.** Root cause #1: `player_agent`'s initial prompt asked a companion to "declare what it does" without ever enumerating the actual verb set, so a "quiet, watchful ranger, slow to warm up to strangers" persona (Silvana) happily generated pure atmosphere - "stays alert, watches the shadows" - forever. Since Day 14 deliberately made "invalid" a no-op that *doesn't* cost a turn (the right call for a human who can just retry), a companion with no human to unstick it just looped on the same non-action every turn. Fixed by rewriting `player_agent.md` to enumerate the same verb set intent_parser's own prompt uses and require exactly one concrete action, plus a `consecutive_invalid` circuit breaker in `cli.play.run_autoplay` that forces `end_turn` after 3 straight non-actions (defense in depth - the prompt fix alone isn't provably 100% reliable against a 7B model). Root cause #2, found immediately after fixing #1: the forced `end_turn` fallback itself was rejected once a companion went unconscious, because `resolve_action`'s top-level guard only accepts `"death_save"` while `hp<=0` - so the circuit breaker's own fallback action failed too, forever, the same infinite loop one layer down. The real fix belongs in `player_agent_node` itself (not just the autoplay script, since live WebSocket play would hit the identical hang the moment a companion goes down): an unconscious-but-not-dead companion is now forced straight to a `death_save` action, skipping the LLM call entirely - there's no narrative content to role-play in "try to stay conscious" anyway. Also gave `run_autoplay` the same `except (TurnEngineError, NotImplementedError)` resilience `api/ws/session.py` already had for human free text (Day 12) - an AI-declared move can still name a non-adjacent destination and get rejected by `movement.py`, and there's no human to phrase it better on retry, so the driver just logs the failure and tries again rather than crashing the whole run.

**Companion-vs-companion friendly fire, confirmed live on the same Day 15 autoplay run, then fixed.** Silvana (an AI companion) attacked Grom (a different AI companion, on her own side) twice in one encounter. This is the same underlying gap Day 12 already flagged for monster free text - `intent_parser`'s "visible characters" list has no notion of allegiance, so an under-specified utterance can resolve to any character id, ally or enemy - now confirmed to hit companion-vs-companion too, not just monster-vs-monster. Rather than patch it at the prompt layer again (no zero-shot prompt tweak can be *guaranteed* to stop a small model from occasionally picking a bad target), fixed it once at the one place both `_resolve_attack` and `_resolve_cast_spell` funnel through: a new `_validate_attack_target` rejects any attack where `target.is_pc == actor.is_pc` (same side, whichever side) before dice are ever rolled - a real game-rule the deterministic engine should own regardless of which upstream LLM call produced the bad target. Two hand-computed regression tests added (PC-attacks-PC, monster-attacks-monster) plus a cast_spell equivalent; the pre-existing "not fixed" monster-vs-monster note above is now closed by this same guard.

**`tests/llm/test_autoplay.py` failed on its first automated run** by hitting `run_autoplay`'s `max_turns` safety valve, even though a manual `--autoplay` run moments earlier finished cleanly (victory in 16 turns). Not a hang or a logic bug - confirmed the turn-advancement invariant holds (a failed/invalid action never advances `state.current_turn`, so the *same* stuck actor is correctly retried and the `consecutive_invalid` circuit breaker does eventually fire for it) - just LLM sampling variance: even with the Day 15 prompt fix, a companion's declaration occasionally still fails to parse, and each such failure burns a turn without landing an attack, which can stretch an already-unlucky combat (bad dice on top of wasted turns) well past a tight turn ceiling. Raised `max_turns` from 200 to 400 as a generous-on-purpose margin rather than chasing full reliability out of a small local model's free-text generation - consistent with `tests/llm/test_intent_parser.py`'s own framing ("LLM output isn't byte-deterministic... tolerant of everything else"). This test can still occasionally need a rerun; that's expected for anything exercising live sampling, not a regression to chase to zero.

**Day 16 - `uv add torch` alone installs a CPU-only wheel; getting the CUDA build needs an *additional* index, not a wholesale replacement of the default one.** `uv add torch --index-url https://download.pytorch.org/whl/cu124` failed dependency resolution entirely - `--index-url` replaces the *default* index for the whole resolve, so `alembic` and everything else in the project suddenly couldn't be found (PyTorch's wheel index only hosts PyTorch-ecosystem packages). Fixed with `uv add torch --index https://download.pytorch.org/whl/cu124` instead, which resolved and installed `torch==2.6.0+cu124` correctly. Note this is *not* as narrowly scoped as it sounds, though: `uv.lock` shows several common transitive deps (certifi, idna, packaging, requests, urllib3, numpy, pillow...) also got pinned to the pytorch index's mirror rather than PyPI, since `--index` adds it as an extra general-purpose index for the whole project, not a source pin restricted to torch alone - confirmed by grepping `uv.lock` for `download.pytorch.org` and finding ~35 packages attributed to it, not just torch. Not a problem in practice (the lockfile pins exact versions either way and everything resolved/tested clean), but worth knowing before assuming `--index` scopes as tightly as `[tool.uv.sources]` normally would. Confirmed live: `torch.cuda.is_available()` -> `True`, `torch.cuda.get_device_name(0)` -> the RTX 3080.

**The critical VRAM-coexistence check (this day's actual gate) passed, but the first measurement attempt gave a false "barely fits" reading purely from tool-timing mistakes, not anything about the GPU.** Querying `nvidia-smi` from separate sequential tool calls around a backgrounded generation script kept catching the process either before it had started or after it had already exited and freed its VRAM - the fix was mundane (run the generation script and a polling `nvidia-smi` loop inside *one* shell invocation, backgrounding the python process with `&` and polling every 3s), not anything about the measurement itself. Once measured correctly: baseline with only `qwen2.5:7b-instruct` loaded was ~5.85GB; with SD-Turbo's pipeline also loaded and a generation in flight, combined usage held steady at ~9.55GB out of 10GB - confirmed live, not estimated (see DECISIONS.md #5). Separately, a `uv run python <script>` invocation using an absolute script path outside the project directory needs either `cd`-ing into the project first or `PYTHONPATH` set explicitly - `pythonpath = ["."]` in `pyproject.toml` only affects `pytest` collection, not arbitrary script runs, so `from src...` failed with a plain `ModuleNotFoundError` until one of those was added.

**A real, load-bearing bug in the VRAM guard: after the very first successful generation, every subsequent scene image for the rest of a session was silently skipped with "Not enough free VRAM."** Caught live running `--autoplay` with real image generation for the first time - only round 1 got an image, rounds 2 onward all logged the skip warning despite the GPU being nowhere near actually out of memory. Root cause: `_has_enough_vram()` was being called before *every* `generate_scene_image()` call, but it checks `torch.cuda.mem_get_info()`'s free-bytes figure - which reports memory free to the *driver*, not to this process specifically. Once SD-Turbo's pipeline is loaded, PyTorch's caching allocator retains the VRAM blocks it already grabbed so it can reuse them for the *next* inference without asking the driver again - which is the whole point of the allocator, but it means "free" stays low from then on even though the already-loaded pipeline needs zero *new* memory to run again. Fixed by moving the VRAM check into `_load_pipeline()` (an `@cache`'d function that only ever runs once per process) so it gates the one-time decision "should we even attempt to load the model" rather than being re-asked on every call; a genuine later OOM is still a real exception caught by `generate_scene_image`'s existing broad except. Re-ran the full autoplay afterward and confirmed all 10 rounds got a scene image, not just the first.

**Verified live: `scene_image_node`'s prompts, built from `game_state.encounter_id` + a same/enemy-labeled character-and-HP summary (no access to the actual `Scene.narrative_intro` text, which isn't threaded into `GraphState` yet), still produced 10/10 images that were visibly on-theme** - armed fighters clashing with green goblin-like creatures in rocky/forested terrain, consistent with "goblin ambush" - spot-checked by eye (5 of 10) rather than assumed. SD-Turbo's 1-step inference can't render specific narrative details (a character being unconscious, an exact HP count), which is an accepted limitation of the "turbo" distillation at this step count, not a prompt bug.

**Day 17 - the Browser pane's `preview_start` reads `.claude/launch.json` relative to this session's own primary working directory (the user's home directory), not wherever a shell has `cd`'d to.** Adding a project-local `.claude/launch.json` in `agentic-dm-engine/` had no effect - `preview_start({name: "backend"})` silently ran an unrelated, pre-existing "web-client" config for a *different* project (`order-fulfillment-platform`) found in the home-directory `launch.json`, since that was the only entry and the name didn't match. Fixed by adding entries to the home-directory `.claude/launch.json` instead, using `uv run --directory <absolute path> ...` and `npm --prefix <absolute path> ...` so each command doesn't depend on any particular starting cwd. Kept the project-local `.claude/launch.json` too (with plain relative commands) since a plain terminal session started with cwd already inside the project would resolve it correctly.

**A brand-new character-creator submission failed with a browser-reported CORS error that had nothing to do with CORS.** The actual cause (visible only in the backend's own logs, not the browser) was `sqlite3.OperationalError: no such table: characters` - the dev SQLite file existed but had never had `alembic upgrade head` run against it in this checkout. Confirmed by reading `preview_logs` for the backend server, not by chasing the CORS message: FastAPI/Starlette's `CORSMiddleware` only attaches `Access-Control-Allow-Origin` to responses that complete normally through it; an unhandled exception (this SQLAlchemy error isn't an `HTTPException`, so `ExceptionMiddleware` doesn't catch it either) propagates past `CORSMiddleware` to the outer `ServerErrorMiddleware`, which converts it to a 500 *without* CORS headers - so the browser reports the symptom (missing CORS header) rather than the cause (a 500). Worth remembering for any future "CORS blocked" report on a route that otherwise has working CORS: check the server's own logs for an unhandled exception before touching the CORS config at all.

**A real, silent data-loss bug in the character-persistence layer, caught by the wizard's own re-fetch-after-create check** (exactly the kind of check Day 17's plan called for, and exactly why it's worth doing for real instead of assuming persistence works). `CharacterRecord` (the SQLAlchemy model, Day 8) predates `Character.class_index` (Day 14, needed for spellcasting-ability lookup) and `Character.skill_proficiencies` (Day 13) - neither field was ever added to the DB model or the two mapper functions (`_character_to_record`/`_record_to_character`), so every character ever created through the API silently lost both fields the moment they round-tripped through the database, for every class, not just spellcasters. First created a Fighter (no spells to lose) and didn't notice; only caught it by deliberately re-fetching and comparing against the create response, which is the actual point of that verify step. Fixed by adding both columns (`skill_proficiencies` needed `server_default='[]'` in the migration specifically - SQLite refuses to add a `NOT NULL` column with no default to a table that already has rows, caught immediately by just running the migration against the existing dev DB) and updating both mapper functions. Re-created a Wizard afterward and confirmed `class_index` and all four `skill_proficiencies` (2 chosen + Acolyte's 2 automatic) survived a real re-fetch.
